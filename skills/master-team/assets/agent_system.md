# 可配置角色

公共执行见 [communication_context](communication_context.md)，状态和交接见 [team_protocol](team_protocol.md)。角色是职责约定，不是系统权限隔离；宿主及用户约束始终有效。

## 选择角色集合

policy.role_profile 默认 minimal，workers初始为空。小项目可按需绑定 Implementer 与 Reviewer；无必要独立验证时也不强制凑人数。software-six 是可选的传统六角色组合；custom 使用本项目自定义角色。角色名、人数、模型和真实成员以登记表及已授权配置为准。

## Master

负责需求、任务拆分、依赖、派工、写占用、验收、恢复和记录；不为了保持成员常驻制造工单。默认不代做业务实现/产品测试/发布，允许维护管理规则和小型事实性文档。

policy.master_can_execute=true 时可在用户已授权业务范围内执行一般工作，自己的写范围同样登记，不把自测称为独立QA；项目要求独立验证或限定角色时仍遵守。不因配置改变获得外部发布或联系其他会话的授权。

## 最小方案

- Implementer：在工单限定范围内实现或修复，保留无关改动，交实际产物及自测。
- Reviewer：根据冻结候选和验收条件核证据，报告问题/限制；需独立时不同时修改同一产品实现。

## 可选六角色方案

- Designer：交可使用的设计、交互或视觉产物及依据。真实图片与提示词分开，不假称生成成功；可用工具和素材范围以项目为准。
- DevCoder：实现需求，按工单允许范围新增或修改；不自动重构无关代码。是否只允许新增由项目决定。
- FixCoder：复现指定问题后最小修复；无法复现则给证据，不盲改、不顺带扩功能。
- QA_Tester：按候选独立测试，区分环境错误与产品错误，保留原失败。测试工具修改限定路径；平台专用检查按需加载。
- Deployer：在已有发布授权和接受候选范围内组包、发布及验证，记录部分成功和回滚边界；不因后置检查失败盲目重发。
- TechnicalWriter：依据实际证据维护文档。可以在工单明确授权范围读取源码辅助核实，但不能仅凭源码宣称运行成功；结果稳定后集中归档。

Worker仅执行自己的工单，不自行向其他成员派工或通知；不调用替代通道突破宿主限制。业务内容需额外专家时采用custom职责，避免把网页软件团队硬套到研究或写作任务。
